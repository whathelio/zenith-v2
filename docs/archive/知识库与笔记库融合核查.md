# 核查：知识库与笔记库融合 + 分流系统冲突

> 两个问题：①知识库和笔记库是否需要融合；②Zenith 的分流系统（日程/知识库）是否有冲突。  
> 基于实际代码：`LibraryView.tsx`、`KnowledgeView.tsx`、`tools.py`、`app.py`。

---

## 1. 知识库 vs 笔记库：是否需要融合

### 现状

| 项 | 笔记库（LibraryView） | 知识库（KnowledgeView） |
|----|----------------------|------------------------|
| 路由 | `/library` | `/knowledge` |
| 数据 | `notes` + `memories` + `skills`（SQLite） | 外部 Chroma 向量库 + LLM Wiki |
| 性质 | 个人动态信息：想法、记忆、技能 | 外部静态文献：PDF/论文/书籍 |
| 变更频率 | 高（随时记） | 低（批量灌入后少改） |
| 检索方式 | 关键词/标签 SQL 查询 | 向量语义检索 |
| 注入方式 | memories 注入 prompt；notes 人工查看 | RAG 片段注入 prompt |

### 结论：**不合并存储，但做交叉引用**

理由：
1. **数据模型不同**：notes 是短文本+标签+来源；向量库是 chunk+embedding+元数据。强行合并会让 schema 膨胀。
2. **变更频率不同**：notes 频繁增删改；向量索引重建成本高，不适合频繁变更。
3. **检索语义不同**：notes 适合精确关键词/标签；知识库适合语义相似。
4. **已有各自最佳入口**：笔记库做个人动态记忆，知识库做文献溯源。

### 建议的“轻融合”

不合并表，但打通交互：
- **笔记 → 知识库**：在笔记详情加“加入知识库”按钮，把笔记内容作为 raw 灌入 RAG（ingest_pdfs 支持本地文件，可扩展支持文本）。
- **知识库引用 → 笔记**：RAG 回答的引用卡片可附带“关联笔记”入口（若 source_file 与某笔记同名）。
- **memories 注入**：已有机制，保持不变；RAG 片段单独注入，不混入 memories。
- **UI**：保持两个入口（📚 笔记库 / 🧠 知识库），避免用户心智混乱。

### 不建议的做法
- ❌ 把 notes 表加 embedding 列混进 Chroma。
- ❌ 把 PDF 文献塞进 notes 表。
- ❌ 用 smart_classify 把文献片段分类成 memory。

## 2. 分流系统：日程与知识库是否冲突

### 现状

Zenith 的“分流”有两层：

#### 2.1 录入分流：`smart_classify` 工具
- 在 `tools.py` 的 `TOOLS_SCHEMA` 里，DeepSeek Function Calling 可调用 `smart_classify`。
- 它把用户输入分流为：`is_plan`（日程）/ `is_thought`（笔记）/ `is_skill`（技能）/ `is_memory`（记忆）。
- **目前没有 `is_knowledge` 分流**。

#### 2.2 对话工具分流：Function Calling
- `/api/chat` 把 `TOOLS_SCHEMA` 传给 DeepSeek，模型自行决定调用 `web_search` / `analyze_content` / `add_schedule` / `smart_classify` / `sync_calendar` 等。
- 知识库工具（`retrieve_docs` / `query_wiki`）尚未合并进 `TOOLS_SCHEMA`。

### 冲突点

| 冲突 | 说明 | 风险 |
|------|------|------|
| 意图歧义 | 用户说“帮我查一下这篇论文讲什么” → 模型可能调 `smart_classify`（当成笔记）或 `web_search`，而不是 `retrieve_docs` | 🟡 中 |
| 日程 vs 知识 | 用户说“明天提醒我读这篇论文” → `is_plan=true` 会建日程，但“这篇论文”需要知识库上下文 | 🟢 低（可先建日程，再附引用） |
| 双重注入 | smart_classify 的 memory 注入 与 RAG 片段注入可能同时发生，prompt 变长 | 🟡 中 |
| 工具爆炸 | 合并后 TOOLS_SCHEMA 工具变多，模型可能选错 | 🟡 中 |

### 结论：**有潜在冲突，但可控，需在 prompt 和工具描述里划清边界**

#### 边界规则建议
1. **知识检索类问题**（“这篇论文…”“文献里有没有…”“总结我看过的资料”）→ 调 `retrieve_docs` / `query_wiki`，不调 `smart_classify`。
2. **录入类输入**（“记一下…”“我决定…”“明天开会”）→ 调 `smart_classify`，不走知识库。
3. **日程+知识混合**（“明天提醒我读论文X”）→ 先 `smart_classify` 建日程，日程描述里可引用知识库来源，但不是本次必做。
4. **memories 注入优先级**：对话 prompt 里 memories 始终注入；RAG 片段仅在调用 `retrieve_docs` 后注入，避免常态叠加。

#### 落地动作（合并工具时一起做）
- 在 `tools.py` 合并 `zenith_rag_tools` 的 schema。
- 更新 `config.py` 的 `SYSTEM_PROMPT`，加一条行为准则：“需要查本地文献/Wiki 时，调用 retrieve_docs / query_wiki；需要记录日程/笔记/记忆时，调用 smart_classify。”
- 工具描述里写清楚 `retrieve_docs` 的适用场景，降低模型选错概率。

---

## 3. 综合建议

1. **不融合存储**，保持笔记库与知识库分离。
2. **做轻交互**：笔记可“加入知识库”，知识库引用可关联笔记。
3. **合并工具时加边界规则**，避免 smart_classify 与 retrieve_docs 互相抢戏。
4. **后续观察**：若模型频繁选错工具，再考虑给 smart_classify 加 `is_knowledge` 字段或单独路由。
