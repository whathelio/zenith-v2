# 代码治理工作流：从文档治理借鉴的编程流程

> 问题：往后的编程工作流程能否借鉴文档治理（doc-governance-review）的流程？  
> 结论：**可以，而且非常适合**。文档治理的核心是“先审计、再动手、最小安全第一刀、可回滚”，这套原则天然适用于代码变更。

---

## 1. 为什么能借鉴

文档治理要解决的问题是：“哪些内容能安全压缩、哪些是承重内容不能动”。
代码治理要解决的问题是：“哪些代码能安全重构、哪些是被依赖的承重逻辑不能动”。

两者本质相同：**在改之前，先把事实和风险搞清楚，再用最小可回滚的方式推进**。

我们这几天其实已经在用这套打法：
- 评审 v3 文档 → 承重缺失点 → 最小安全第一刀
- 目标 UI 灰度收敛 S1–S4 → 每步可 `git checkout` 回滚
- 依赖映射 → 检查幽灵组件
- /knowledge 验收标准 → 明确“成功”定义

---

## 2. 文档治理 → 代码治理 映射表

| 文档治理步骤 | 代码治理对应 | 代码场景具体动作 |
|--------------|--------------|------------------|
| Step 1: Index & Scope | 范围与索引 | 列出要改的文件/模块/入口；识别配置、路由、Context、数据库表 |
| Step 2: Fact Confirmation | 事实确认 | 读代码，确认实际行为、版本、测试覆盖、被谁依赖；不靠记忆 |
| Step 3: Risk Reasoning | 风险推理 | 找承重代码（被硬依赖、被断言、被外部调用）；列出破坏性变更 |
| Step 4: Output Report | 变更方案 | 输出：承重缺失点 + 最小安全第一刀 + 分阶段计划 + 验收标准 + 回滚预案 |
| 四种状态 | 四种状态 | `[已核实事实]` 代码实际行为 / `[基于事实的推理]` 影响推断 / `[你的判断]` 主观评估 / `[仍需人工拍板]` 高风险决策 |
| 最小安全第一刀 | 最小改动 | 不删旧实现、先加抽象层、配置切换、保留回滚路径 |
| 分阶段 A–E | 灰度实施 | A 优先核心 → B 并行 → C/D/E 后续；每步独立可验证 |
| 红队自检 | 红队自检 | “假设这次改动导致测试失败/页面白屏，如何回滚？这是最小安全第一刀吗？” |
| 人类决策清单 | 决策清单 | 技术可行性 + 业务交付 + 决策签字 |
| READ ONLY | 先读后写 | 评审阶段不改代码；改代码阶段每步可 `git checkout` |

## 3. 代码治理工作流模板（建议作为后续每次重构的标准流程）

### 阶段 0：需求与范围
- 用一句话写清“这次要解决什么问题”。
- 列出涉及的文件/模块/路由/表/依赖。
- 明确不在本次范围内的东西。

### 阶段 1：事实核查（READ ONLY）
- 实际读代码，不要靠记忆。
- 确认：入口、数据源、状态管理、被依赖关系、测试现状。
- 每条结论打状态：`[已核实事实]` / `[基于事实的推理]` / `[你的判断]` / `[仍需人工拍板]`。

### 阶段 2：风险与承重识别
- 哪些是承重代码（被硬依赖、被外部调用、被断言）。
- 哪些是“幽灵组件”（定义了但没人用）。
- 哪些是重复实现（如 ChromaStore 两份）。
- 哪些改动是破坏性的、不可逆的。

### 阶段 3：最小安全第一刀
- 不要求一步到位。
- 先加抽象/代理/接口，不删旧实现。
- 给出“可一键回滚”的具体命令（`git checkout xxx`）。
- 红队自检：假设失败，能否回滚？

### 阶段 4：灰度实施
- 按阶段推进，每步只动一个文件/一个模块。
- 每步验证：`tsc --noEmit` + `vite build` + 冒烟测试。
- 通过后再下一步；不通过就 `git checkout` 回滚。

### 阶段 5：验收标准
- 功能验收：列具体场景与预期行为（像 K1–K8）。
- 非功能验收：性能、安全、兼容。
- 回归验收：原有功能未被破坏。

### 阶段 6：收尾
- 更新记忆/文档。
- 标注 TECH-DEBT。
- 下一阶段触发条件。

---

## 4. 安全规则（照搬文档治理）

1. **先读后写**：评审阶段不改代码。
2. **增量提交**：add → delete → modify 分开提交，不要一个大 commit。
3. **不批量删**：不先删后修，保留旧实现直到新实现验证通过。
4. **测试通过 ≠ 语义安全**：`tsc`/`build` 通过只代表编译过，不代表行为正确。
5. **每步可回滚**：每个改动都对应一条 `git checkout` 命令。

---

## 5. 实例：本次 Zenith 目标 UI 收敛就是这套流程

| 阶段 | 实际动作 |
|------|----------|
| 范围 | 目标状态三处重复，显示字段不统一，激活入口分散 |
| 事实核查 | 读 AppLayout/CalendarView/GoalsView/Context，确认三处各调 loadGoals |
| 风险 | 承重：Context 已存在但未被消费；重复 ChromaStore；GoalsView 显示全部目标 vs Context 只 active |
| 最小第一刀 | S1 只改 CalendarView，不删其他 |
| 灰度 | S1→S2→S3→S4，每步 tsc+build 验证 |
| 验收 | 数据源单一、显示字段全局、激活入口单一 |
| 回滚 | 每步 `git checkout features/xxx.tsx` |

---

## 6. 一句话总结

> **文档治理的“先审计、承重识别、最小安全第一刀、灰度、可回滚、人类决策清单”这套流程，可以直接作为后续所有编程变更的标准工作流。它不是额外负担，而是减少返工和线上事故的护栏。**

---

## 7. 是否需要做成 Skill

如果希望以后每次重构/新功能都自动走这套流程，可以把它蒸馏成一个 `code-governance-workflow` 技能：
- 触发词：重构、改动评估、上线前评审、代码治理、变更方案
- 输出：事实核查表 + 承重风险表 + 最小安全第一刀 + 灰度步骤 + 验收标准 + 回滚预案
