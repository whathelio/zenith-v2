## 三、问题详述

### 🔴 F-01　`backend/_archived/` 是活依赖，不是死代码

**证据**

```
backend/calendar_sync.py:14    from ._archived.jin10_service import get_jin10_service   ← 模块级顶层导入
backend/routers/news.py:60     from .._archived.jin10_service import Jin10Service        ← 惰性导入
backend/scripts/probe_jin10.py:26  from backend._archived.jin10_service import ...       ← 脚本
```

实测导入链：
```
✅ calendar_sync 导入成功，get_jin10_service = <function get_jin10_service at 0x...>
✅ _archived.jin10_service 可导入（命名空间包，无 __init__.py）
```

且该路径是**活跃业务链路**：`scheduler._calendar_sync_loop` → `sync_calendar_events()` → `get_jin10_service()`，`schedule_events` 表最新数据为今日 08:00。

**根因**：归档时只做了「目录改名」，没有切断引用。`_archived/` 无 `__init__.py`，靠 Python 3 命名空间包隐式生效——这层隐式性让依赖更隐蔽。

**风险**：任何"清理归档目录"的动作（此前评估中曾列为可删除）会让 `import app` 直接抛 `ModuleNotFoundError`，**服务完全无法启动**，且报错点不在归档目录本身，排查成本高。

**建议**：把 `jin10_service.py` 从 `_archived/` 移回 `backend/`（或抽出 `Jin10Service` 中日历同步真正需要的 `_mcp_post` / `list_calendar` 两个方法到新模块 `backend/jin10_client.py`），再改 3 处 import。**在依赖切断之前，`_archived/` 标记为不可删除。**

**Rollback**：`_archived/` 仅重命名，反向 `mv` 即可复原。

### 🔴 F-02　MCP 配置路径错位，MCP 桥静默为空

**证据**

```
config.yaml:        mcp.workbuddy_config_path: ${WORKBUDDY_CONFIG_DIR}/mcp.json
env:                WORKBUDDY_CONFIG_DIR = D:\WorkBuddyData\.workbuddy
解析结果:            D:\WorkBuddyData\.workbuddy\mcp.json   → 文件存在: False
真实文件位置:        C:\Users\xiepu\.workbuddy\mcp.json       → 268 bytes，含 1 个 server
```

`GET /api/modules/mcp` → `{"servers": [], "count": 0, "enabled": 0, "source": "config"}`
`GET /api/modules/mcp/health` → `{"servers": [], "count": 0, "ok": 0, ...}`

真实配置内容（脱敏）：
```json
{ "mcpServers": { "mt5-terminal": { "serverUrl": "http://127.0.0.1:22346/mcp", "headers": {"Authorization": "Bearer ***"} } } }
```

**根因**：`WORKBUDDY_CONFIG_DIR` 指向的是 WorkBuddy **应用数据目录**（`D:\WorkBuddyData\.workbuddy`），而 `mcp.json` 实际落在**用户主目录**（`C:\Users\xiepu\.workbuddy`）。两者不是同一个目录，配置模板的假设不成立。

**风险**：MCP 能力在 Zenith 内**完全不可用且无任何报错**——`load_mcp_servers()` 在文件不存在时回落到 `config.yaml` 的 `mcp_servers: []`（空数组），于是"没配 MCP"和"配了但找不到"呈现为同一种静默状态。Dashboard 的 `mcp_servers: 0` 是唯一线索。

**建议**（二选一，推荐 A）：
- **A**：`config.yaml` 的 `workbuddy_config_path` 改为绝对路径 `C:/Users/xiepu/.workbuddy/mcp.json`
- **B**：`get_mcp_config_path()` 增加候选路径回退链（`$WORKBUDDY_CONFIG_DIR/mcp.json` → `~/.workbuddy/mcp.json`），并在文件缺失时 `logging.warning` 显式告警

无论选哪个，都应补一条**启动时自检**：路径解析不到就写 WARN 日志，避免继续静默。

**Rollback**：仅改一行 YAML，可随时还原（已有备份 `data/backup/config.yaml.bak-20260910-130751`）。

### 🟡 F-04　`skills_dir` 指向空目录，技能扫描恒为 0

**证据**

```
config.yaml:  skills_dir: D:\WorkBuddyData\.workbuddy\skills
该目录:        存在，但顶层条目 = 0
Dashboard:    {"skills": 50, "mcp_servers": 0, "mcp_enabled": 0, "skill_files": 0}
```

技能文件实际分布（`.workbuddy` 下共 1264 个 `SKILL.md`）：

| 位置 | 数量 |
|---|---|
| `plugins/marketplaces` | 628 |
| `connectors-marketplace/connectors` | 469 |
| `plugins/cache` | 160 |

**根因**：`skills_dir` 配置的是 WorkBuddy 的**用户级技能目录**，但该目录当前为空；技能实际分散在 `plugins/marketplaces`、`connectors-marketplace` 等 4 个位置。

**建议**：先明确 `skills_dir` 的**语义**——是要指向用户自建技能、还是全量技能库？若是后者，需要支持多目录扫描（`skills_dirs: [...]`）并排除 `binaries/node` 这类非技能目录。

### 🟡 F-05　删除目标不清理关联日程，产生悬挂引用

**证据**

```
schedules 表:  id=36, title='目标关联测试', goal_id=1, start_time='2026-07-17T22:00:00+08:00'
goals 表:      实际行数 = 0        ← 目标 1 已不存在

database.py / goal_del():
    def goal_del(gid: int):
        with db() as c:
            c.execute("DELETE FROM goals WHERE id = ?", (gid,))     ← 只删 goal 自己
```

且 `schedules` 建表语句**未声明 FOREIGN KEY**：
```
goal_id INTEGER DEFAULT NULL      ← 无 REFERENCES 约束
```
所以 `PRAGMA foreign_key_check` 报 0 违规（SQLite 根本不知道这层关系），问题不会被自动发现。

**建议**：`goal_del` 内补 `UPDATE schedules SET goal_id = NULL WHERE goal_id = ?`。存量脏数据 1 条可顺手清理。

### 🟡 F-07　记忆 `created_at` 历史缺口

**证据**

| created_at 状态 | 行数 | 集中在 |
|---|---|---|
| NULL | 1164 | **全部为 2026-07** |
| 非 NULL | 925 | 07 月 265 / 08 月 608 / 09 月 52 |

**关键判据：8 月起 100% 完整写入**，说明当前代码已正确（`mem_add` 写 `_now()` → ISO 格式），这是**历史回填缺口，不是活跃 bug**。

**真实影响链**：
```
mem_list_by_date(date_from, date_to)          ← 用 substr(created_at,1,10) 过滤
  └─ unified_distill.py:164  日报记忆段
  └─ unified_distill.py:262  周报记忆段
```
→ 对 **2026-07** 区间重跑日报/周报蒸馏，会漏掉这 1164 条记忆。日常增量蒸馏不受影响。

**建议**：`mem_list_by_date` 改为 `COALESCE(created_at, recorded_at)` —— `recorded_at` 字段 100% 有值，可彻底消除该缺口。若要保持历史一致，另做一次一次性回填。

### 🟢 F-09　记忆时间字段格式混用

`created_at` 的三种形态：

| 形态 | 行数 | 样例 |
|---|---|---|
| NULL | 1164 | — |
| ISO（`T` 分隔） | 612 | `2026-09-10T13:15:36.855876+08:00` |
| 空格分隔 | 301 | `2026-08-26 20:44:35` |
| **纯数字垃圾值** | **12** | `'39'`、`'66'`、`'59'`、`'62'`、`'61'`、`'60'`、`'53'`、`'48'` |

12 条垃圾值全部落在 2026-07-17 ~ 07-19。副作用：`substr(created_at,1,10)` 得到 `'39'`，字典序 `'3' > '2'`，因此**任何日期下界筛选都会命中这 12 条**。

**建议**：一次性清理这 12 条（用对应 `recorded_at` 覆盖），并统一为 ISO 格式。低优先级。

## 四、架构观察

**做得好的地方**

1. **前后端接口零断链** —— 82 条前端调用全部有后端实现，无 404。
2. **封存有优雅降级** —— CFTC 返回 410 + 明确文案，而不是 500 或静默空数据。
3. **路由模块化彻底** —— 15 个 router 全部正确挂载，无遗漏。
4. **静态检查干净** —— `tsc -b` + `vite build` 无警告。
5. **数据完整性良好** —— `integrity_check` = ok，无 FK 违规。
6. **后台任务面清晰** —— 7 个 loop（提醒 / 记忆维护 / daily-weekly-monthly-yearly 蒸馏 / 日历同步）职责分明。
7. **发布守卫到位** —— `validators/` 下 6 个守卫模块（input/output/execution/auditor/noise/sanitize），`mem_add` 有明文密钥拒写守卫。

**结构性风险**

1. **`app.py` 是个 67 路由的单体** —— 其中 11 条 market + 6 条 mt5 本可独立成 router。`app.py` 已承载过多职责。
2. **归档机制不可靠** —— `_archived`（185K）+ `_archive_cleanup_20260825`（1.4M）两处并存，且前者含活依赖。归档前缺少「引用切断」检查步骤。
3. **静默失败模式** —— F-02（MCP 路径错）和 F-04（skills_dir 空）都是"配置错误 → 回落到空 → 无告警"。建议给这类配置解析加统一的自检告警。
4. **配置双源** —— 模型/Provider 在 `config.yaml`，密钥在 `.env`，MCP 在外部 `mcp.json`，`skills_dir` 又在 yaml。三处路径假设互相独立，容易错位。

## 六、复核方法（可复现）

| 手段 | 覆盖 |
|---|---|
| 路由枚举 | 正则扫描 `@app/@router` 装饰器，含 `APIRouter(prefix=)` 拼接 → 159 条声明 / 124 条归一化路径 |
