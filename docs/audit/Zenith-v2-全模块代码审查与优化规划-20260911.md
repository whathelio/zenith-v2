## 3. 严重问题清单（按优先级）

### 3.1 🔴 P0 — 必修

#### P0-1 ｜ `msg_del_from` 跨会话误删（**正在丢数据**）✅已验证

`backend/database.py:845-854`

```python
def msg_del_from(msg_id: int) -> int:
    with db() as c:
        row = c.execute("SELECT conversation_id FROM messages WHERE id = ?", (msg_id,)).fetchone()
        cur = c.execute("DELETE FROM messages WHERE id >= ?", (msg_id,))   # ← 无 conversation_id 过滤
```

`messages.id` 是**全局自增**，跨会话连续。`WHERE id >= ?` 会删掉**所有会话**中 id 更大的消息。

三个调用点全部命中：
- `routers/chat.py:737`（`/chat/regenerate`）
- `routers/chat.py:775`（`/chat/edit`）→ `msg_del_from(msg_id + 1)`，**删除该消息之后的全库消息**
- `routers/chat.py:791`（`DELETE /chat/messages/{id}?mode=tail`）

**场景**：在旧会话里点一次「编辑重发」→ 新建的会话消息被静默清空。当前 `messages` 682 行、107 会话，风险敞口真实。

**修复**：加 `AND conversation_id = ?`，并传所属会话 id（函数已经在查这一列，只是没用上）。约 3 行改动。

#### P0-2 ｜ 同步阻塞仍在事件循环上（历史"假死"同款根因）✅已验证

| 位置 | 问题 |
|---|---|
| `backend/scheduler.py:129` | `mem_consolidate()` **直接调用**在 `_memory_maintenance_loop` 的 async 函数里。每 6 小时执行：全量 `mem_list` + 最多 50 次 `mem_search` + numpy 相似度，全程占住事件循环 → 期间所有 HTTP 请求 stall。同文件其他任务已用 `to_thread`，此处漏改。 |
| `memory_engine.py:87 → 601 → 559/399` | `build_memory_injection` 由 `chat.py:609` **每条消息同步执行**：2 次 `COUNT`（IDF/gram 缓存刷新判定）+ 全量记忆 n-gram 打分。 |
| `app.py:1426-1468` | 6 条 `/api/mt5/*` async 路由直接调用同步 MT5 IPC。 |
| `validators/output_validator.py:76` | 每条回复跑 `mem_search` + numpy 相似度。 |

**背景**：2026-08-25 三次"假死"的真凶就是 consolidate 的 O(n²) 同步跑在事件循环（`data/watchdog_stack_*.log` 为证）。已修算法，但**未统一挪出事件循环**，同款模式仍在。

**修复**：`asyncio.to_thread(...)` 包裹；IDF/gram 缓存改 TTL 或写侧失效，避免每轮 `COUNT`。

## 7. 勘误（2026-09-11 追加，实测推翻两项记录数据）

原 §4.2 引用「缓存命中率当前仅 1.9%」并据此把「提命中率」列为最大成本杠杆。**该引用错误**——源自对既有记忆条目的误读（把「成本占比」当成了「命中率」）。实测更正：

| 指标 | 原记录（误） | 实测（正确） |
|---|---|---|
| 缓存命中率 | 1.9% | **62.46%**（命中 5,331,328 / 输入 8,535,231） |
| 前台 chat 命中率 | — | **66.2%**（533 次调用） |
| 后台 background 命中率 | — | **18.6%**（81 次调用） |
| 「1.9%」的真实含义 | 被当作命中率 | 缓存命中输入**在总成本中的占比**（与未命中输入 56.5% + 输出 41.6% 相加 = 100%） |

**优化方向随之修正**：命中率**不是**最大杠杆（命中输入只占总成本 1.9%，且命中率已达 62.5%）。真杠杆是：

| 杠杆 | 成本占比 | 等价含义 | 实测基线 |
|---|---|---|---|
| 未命中输入 | **56.5%** | prompt 体积 | 单轮平均输入 **≈13.9K tokens** |
| 输出 | **41.6%** | 输出长度 | chat 单轮平均 **923 tokens** 输出 |

## 8. 关于「换语言 / 换现代企业化语言」的结论（2026-09-11 追加）

**结论：不建议换。** 实测证据链：

| 项 | 实测值 | 数据来源 |
|---|---|---|
| 本地端点延迟 | **p50 1.3–1.6 ms**，p95 ≤ 2.4 ms（9 端点 × 20 次，持久连接） | `tools/audit/latency.py` |
| LLM 输出吞吐 | **51.5 tok/s**（deepseek-flash，关思考） | `tools/audit/llm_throughput.py` |
| chat 单轮平均输出 | 923 tokens → 纯生成 **≈18 s** | `cache_stats` 折算 |
| **本地代码在单轮时延中的占比** | **≈ 0.005%**（2 ms / 18 s） | 上两项 |

即使把 Python 换成 C/Rust 让本地代码快 10 倍，单轮也只省约 2 ms（≈0.01%）；**成本侧同样与语言无关**——6.61 元全部是 LLM token 费用，编译器写什么语言都不产生费用。

**真正的「企业化」缺口是工程实践，不是语言：**

| 缺口 | 实测 | 影响 |
|---|---|---|
| 请求体无 schema 校验 | `pydantic 2.13.4` 已装但**代码 0 引用**；5 处裸 `await request.json()` | `Body(default=None)` 直接 `.get` → 空 body 触发 500（见 §3.2） |
| 无静态类型检查 | 无 mypy；返回标注覆盖 **405/676 = 60%**，`app.py` 仅 1 处 | 大重构（如 §5 Phase 3 拆分）缺少编译期安全网 |
| lint 仅错误级 | `pyproject.toml` 只启用 `F/E4/E7/E9` | 无法自动拦截未使用变量/未标注等 |
